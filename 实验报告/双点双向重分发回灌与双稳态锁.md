# 双点双向重分发回灌与双稳态锁

> 2026 年 11 月 11 日，eNSP 实验复盘
> 一个"配好就没管它，但现象却讲不通"的典型：为什么 R1 上 5.5.5.5 的回灌来自 R3 而不是 R2。

# 一、实验拓扑

```
                    OSPF 区域 0                     IS-IS 49.0001
                                                    
     R5 ──10.0.15.0/24── R1 ──10.0.12.0/24── R2 ──10.0.24.0/24── R4
                          │                   │                    │
                          └──10.0.13.0/24── R3 ──10.0.34.0/24──────┘
```

| 设备 | 角色 | Router-ID / NET | 接口 |
|---|---|---|---|
| R1 | 纯 OSPF | 1.1.1.1 | 10.0.12.1、10.0.13.1、10.0.15.1 |
| R2 | OSPF/IS-IS ASBR | 2.2.2.2 / 49.0001.0000.0000.0001.00 | 10.0.12.2、10.0.24.2 |
| R3 | OSPF/IS-IS ASBR | 3.3.3.3 / 49.0001.0000.0000.0003.00 | 10.0.13.3、10.0.34.3 |
| R4 | 纯 IS-IS | — | 10.0.24.4、10.0.34.4 |
| R5 | 外部路由源 | 5.5.5.5 | 10.0.15.5 |

关键配置（四台的两两引入）：

```
# R1 —— 只跑 OSPF，把直连引入
ospf 1 router-id 1.1.1.1
 import-route direct route-policy di
#
# R2 —— 双点双向引入
isis 1
 network-entity 49.0001.0000.0000.0001.00
 import-route ospf 1
ospf 1 router-id 2.2.2.2
 import-route isis 1
#
# R3 —— 双点双向引入（与 R2 完全对称）
isis 1
 network-entity 49.0001.0000.0000.0003.00
 import-route ospf 1
ospf 1 router-id 3.3.3.3
 import-route isis 1
#
# R5 —— 外部路由源
ospf 1
 import-route direct
```

> 注意：R2、R3 的两条 `import-route` **都没有指定 cost，也没打 tag**。这是后面所有问题的根源之一。

# 二、现象

R1 上 5.5.5.5 是两条等价路由，下一跳分别是 10.0.15.5（R5 直连注入）和 **10.0.13.3（R3）**，而**不是** 10.0.12.2（R2）。

```
[R1] display ip routing-table 5.5.5.5 verbose
  Destination: 5.5.5.5/32
     Protocol: O_ASE   Preference: 150   Cost: 1   NextHop: 10.0.15.5   GE0/0/2
  Destination: 5.5.5.5/32
     Protocol: O_ASE   Preference: 150   Cost: 1   NextHop: 10.0.13.3   GE0/0/1
```

```
[R1] display ospf lsdb ase 5.5.5.5
  Adv rtr: 10.0.15.5   seq# 0x80000001   metric 1   Tag 1     ← R5 直连
  Adv rtr: 3.3.3.3     seq# 0x80000006   metric 1   Tag 1     ← R3 回灌
  没有 2.2.2.2                                                 ← R2 没回灌
```

疑问：R3 也做了 IS-IS→OSPF 引入，为什么这条不是 R2 从 IS-IS 学回来再回灌的？

---

# 三、答案：两台设备的角色被 RIB 自动分工了

```
[R2] display isis route   Level-2 Redistribute Table
  D  10.0.12.0/24   0  0
  O  10.0.13.0/24   0  0
  O  5.5.5.5/32     0  0    ← 有：R2 负责 OSPF→IS-IS
  O  10.0.15.0/24   0  0

[R3] display isis route   Level-2 Redistribute Table
  D  10.0.13.0/24   0  0
  O  10.0.12.0/24   0  0
  O  1.1.1.1/32     0  0
  O  10.0.15.0/24   0  0    ← 没有 5.5.5.5：R3 不往 IS-IS 里注入它
```

再看两台 RIB 里这条前缀的归属：

```
[R2] display ip routing-table 5.5.5.5 verbose
  O_ASE    150  Cost 1   NextHop 10.0.12.1   Active     ← OSPF 版本生效

[R3] display ip routing-table 5.5.5.5 verbose
  ISIS-L2   15  Cost 84  NextHop 10.0.34.4   Active     ← IS-IS 版本生效
  O_ASE    150  Cost 1   NextHop 10.0.13.1   Inactive   ← OSPF 版本被压掉
```

结论：

| 设备 | RIB 里生效的版本 | `import-route ospf` | `import-route isis` |
|---|---|---|---|
| R2 | O_ASE Active | ✅ 有东西可注入 | ❌ 无 IS-IS 路由 |
| R3 | ISIS-L2 Active | ❌ 无活跃 OSPF 路由 | ✅ 有东西可注入 |

**一条路径各管一个方向，互相成全，谁也不会打破。** 这叫"双稳态锁定"。

# 四、核心概念链

理解这个现象需要一条完整的概念链，缺一环就会绕不出来。

## 1. 三层路由数据，不要混为一谈

| 层         | 命令                                            | 内容                | 用途          |
| --------- | --------------------------------------------- | ----------------- | ----------- |
| **LSDB**  | `display ospf lsdb` / `display isis lsdb`     | 所有设备通告的原始 LSA/LSP | 跑 SPF 的原料   |
| **协议路由表** | `display ospf routing` / `display isis route` | 单协议 SPF 算出的候选集    | 交给 RIB 参选   |
| **RIB**   | `display ip routing-table`                    | 跨协议比完后的裁决         | 下发 FIB，实际转发 |

R3 上三层**全都有** 5.5.5.5，但重分发只认第三层。

## 2. RIB 是唯一裁判，preference 是唯一规则

```
Direct 0 < OSPF 10 < IS-IS 15 < Static 60 < RIP 100 < OSPF ASE 150 < BGP 255
```

RIB 里同时存在两条 5.5.5.5：

```
O_ASE     Pref 150   Cost 1     ← cost 只有 1
ISIS-L2   Pref 15    Cost 84    ← cost 高达 84
```

**IS-IS 赢不是因为路径短，而是因为 15 < 150。**

不同协议的 cost 是不同量纲（OSPF 是带宽倒数，IS-IS 是接口缺省值累加），**跨协议只比 preference，不比 cost**。preference 相同才比 cost，都相同才 ECMP。

## 3. Active / Inactive 与 D 位

```
Active    = 选中，已下发 FIB，可以转发，可以重分发
Inactive  = 落选，保留在表里只作快速收敛备份，不能重分发
```

`display ip routing-table x.x.x.x verbose` 里的 `Flags: D`（Download to FIB）就是"胜出并生效"的标记。重分发谓词只认带 D 的条目：

```
Proto == OSPF && ProcessID == 1 && D位 == 1
```

## 4. 自己注入的路由不回流自己的 RIB（水平分割）

```
[R2] display isis route  →  Redistribute Table 里有 O 5.5.5.5/32
[R2] display isis route  →  Forwarding Table 里没有 5.5.5.5
```

R2 把 5.5.5.5 放进自己发出的 LSP，但**不会把自产的 IS-IS 前缀再装回自己 RIB**。所以 R2 的 OSPF 副本永远是 Active，R2 永远持有"OSPF→IS-IS"这个角色。

**这一条 + preference 压制 = 不对称锁定**：先注入的一方不会因自己的注入而失去触发源，后到的一方被永久压制。

## 5. 双稳态（bistable latch）

| | R2 | R3 |
|---|---|---|
| 稳定态 A（本实验） | OSPF→IS-IS | IS-IS→OSPF |
| 稳定态 B（镜像） | IS-IS→OSPF | OSPF→IS-IS |

两个都是合法收敛态，都不会成环。落在哪一侧由**毫秒级时序**决定，之后靠协议自身的周期刷新永久固化。

中间态（两台都双向）**逻辑上自相矛盾**：如果两台都注入 IS-IS，两台都收到对方的 IS-IS 副本，两台 OSPF 副本同时消失，两台都撤回，谁也维持不住。所以中间态只能短暂存在。

# 五、为什么会"反复"——重分发反馈环

不是"一台快一点就赢"，而是存在正反馈环：

| 时刻 | R2 | R3 |
|---|---|---|
| T0 | 5.5.5.5 = O_ASE **Active** | 5.5.5.5 = O_ASE **Active** |
| T1 | 注入 IS-IS，LSP 带 5.5.5.5，ExtCost 0 | 同样注入 |
| T2 | 收到 R3 的 LSP → IS-IS 副本压过 OSPF → **Inactive** | 同样被压成 Inactive |
| T3 | `import-route ospf` 抓不到 → 重建 LSP，丢掉 5.5.5.5 | 同样丢掉 |
| T4 | 收到 R3 的撤回 → IS-IS 副本消失 → OSPF 回 **Active** | 同样回 Active |
| T5 | **重新注入** | **重新注入** |
| → T2 | 循环 | 循环 |

关键在于 **T3 是两台同时撤回**，撤回后两台又同时恢复 OSPF 副本，环自我维持。

"一台快一点"只在**环的出口**成立：某一轮里 A 的新 LSP 到达 B 的时刻早于 B 执行注入，B 就被压住且不再注入，A 因为永远收不到 B 的 LSP 就一直注入。**决定的是最后那一轮。**

## 锁定证据：序列号

```
R5 直连：   seq# 0x80000001
R3 回灌：   seq# 0x80000006
```

Type-5 初始序列号是 `0x80000001`，每**重新产生**一次 +1，到 `0x7FFFFFFF` 回绕。

准确解读：
- 只能证明 **R3 这条 LSA 被重新产生过 5 次**
- **不等于撤销过 5 次**——撤销（flush）是用同一序列号把 Age 置 3600 发出去，**不 +1**
- +1 的时机：路由重新出现，或 LSA 内容变了（metric、FA、tag）

所以它可能是"撤销-重发"的抖动，也可能是手敲配置时 RIB 反复变化留下的（R3 重分发表里 10.0.12.0、1.1.1.1 进进出出，每次都会重生 LSA）。

## 看不到抖动的原因

环的周期是 **几十到几百毫秒**，而 `display` 需要几秒。等你看到时早已锁定。

想真的看到它抖，只能采样：

```
terminal monitor
terminal debugging
debugging ospf lsa
debugging isis lsp
undo debugging all        # 收工务必关掉
```

# 六、LSP 机制细节

## 1. IS-IS 的发布单位是整条 LSP，不是单条前缀

OSPF 一条前缀一个 LSA；IS-IS 把**一个节点的所有路由信息打包成一条 LSP**：

```
LSP (System ID 0000.0000.0003, seq 0x0000000A)
 ├── TLV 22   邻接关系（邻居、metric）
 ├── TLV 135  扩展 IP 可达性
 │     ├── 10.0.34.0/24
 │     ├── 10.0.13.0/24
 │     ├── 1.1.1.1/32
 │     ├── 10.0.15.0/24
 │     └── 5.5.5.5/32      ← 只是其中一个条目
 └── TLV 132  接口地址
```

所以"撤回 5.5.5.5"实际是：重分发表重算 → 重新生成**整条 LSP**，序列号 +1 → 泛洪。对端收到高序列号后**整条替换**，跑 SPF，发现少了这一项。

**没有"删除单个前缀"的报文。** 如果恰好只差这一条，看起来像精确删除，机制上永远是整包重发。

## 2. LSP 里少一条前缀的三种可能，只有一种符合

| 机制 | 触发 | 粒度 | 序列号 | 本实验 |
|---|---|---|---|---|
| **内容变更重生** | 重分发表/邻接/接口状态变了 | 单前缀 | **+1** | ✅ 就是这个 |
| **Purge（清除）** | 剩余寿命置 0 主动清除 | **整条 LSP** | 不 +1 | ❌ |
| **老化/刷新失败** | 900s 不刷新、1200s 寿命到 | **整条 LSP** | 不 +1 | ❌ |

**决定性反证**：R3 的重分发表里其他三条（10.0.12.0、1.1.1.1、10.0.15.0）都还在。如果 LSP 被老化或清除，这四条会同时消失，并且会触发邻居 down + SPF 重建。实际只掉了一条。

## 3. 定时器时间尺度（差两个数量级）

| 定时器                              | 默认值        | 作用                       |
| -------------------------------- | ---------- | ------------------------ |
| LSP Refresh（`timer lsp-refresh`） | **900 s**  | 到点重新泛洪，**序列号不变**，只重置剩余寿命 |
| LSP Max Age（`timer lsp-max-age`） | **1200 s** | 剩余寿命归零 → 对端视为失效          |
| Zero Age Lifetime                | 600 s      | 归零后还保留多久才真正删除            |
| **LSP-Throttle**                 | **50 ms**  | 两次重生之间的最小间隔              |

**反直觉点：IS-IS 周期刷新不涨序列号。** 所以 `0x80000006` 完全不可能是"刷了 6 次"，只能是"**内容变了 6 次**"。

从引入到锁死只用了**几秒**，而 AGE 才 5~9 分钟，900s/1200s 的定时器根本来不及动。

## 4. LSP-Throttle 是什么

IS-IS 路由一变就要生成新 LSP（序列号 +1）并泛洪。如果内容在极短时间内反复变（就像上面那个环），每次立刻生成会打爆 CPU 和带宽。所以加了限速：

> **`timer lsp-throttle` = 同一条 LSP 两次生成之间的最小间隔，默认 50ms。间隔内的多次变更会攒着，到点合并成一次生成。**

它是"**合并**"不是"丢弃"。在设备上的样子：

```
display isis brief
  Timers:  Csnp: L1 10  L2 10 , Retransmit: L12 5 , Hello: L1 10 L2 10 ,
  Hello Multiplier: L1 3  L2 3 , LSP-Throttle Timer: L12 50
```

各字段含义：

| 字段                        | 含义                     |
| ------------------------- | ---------------------- |
| `Csnp 10`                 | DIS 每 10 秒发 CSNP 同步数据库 |
| `Retransmit 5`            | 点对点未确认 5 秒重传           |
| `Hello 10 × Multiplier 3` | 邻居 Hold = 30 秒         |
| `LSP-Throttle 50`         | LSP 重生最小间隔 50ms        |

**它决定了撤回和重新注入最快能多快，也就是那场毫秒级赛跑的时间分辨率。**

相关命令：

```
display isis timer              # Hello / CSNP / PSNP / LSP 各类定时器
display isis timer lsp          # LSP 生成、刷新、老化
isis 1
 timer lsp-throttle 100          # 默认 50ms，范围 0~1000
 timer spf 50 200 5000           # SPF 初始/增量/最大
```

## 5. TLV 135 的编码细节

```
TLV 135 (5.5.5.5/32)
 ├─ metric      = 外部 cost（本实验 0，因为 import-route ospf 1 没给 cost）
 ├─ X 位        = 1   ← "这条是从 IS-IS 外部重分发进来的"
 ├─ R 位        = 是否重分发到其他 level
 ├─ 前缀长度 32 + 5.5.5.5
 └─ sub-TLV: 32-bit tag（本实验为空，Admin Tag: -）
```

**ExtCost 默认 0 是这个环能轻易锁死的一大原因**：外部代价 0 意味着这条在 IS-IS 域内不比任何直连更贵。规范做法是 `import-route ospf 1 cost 20`。

## 6. 对端选路的比较顺序

```
第一比：Level     同前缀 L1 和 L2 都有 → 默认 L1 优先
第二比：metric    IntCost（到通告者的 SPF 距离）+ ExtCost
第三比：相等则 ECMP（最多 8 条）
```

**全程没有"哪个协议"参与**，到这一步所有候选都是 IS-IS 自己的 LSP，只比 cost。

本实验实测：

```
[R3] display isis route 5.5.5.5 verbose
  Int.Cost 20   Ext.Cost 0   Src Count 1
  NextHop 10.0.34.4   Flags : A/-/-/-
```

IntCost 20 = R3→R4 的 10 + R4→R2 的 10。

# 七、Flags 五位速查（重点看 L）

| 位     | 含义                                 |
| ----- | ---------------------------------- |
| **D** | Direct，SPF 树的叶子（直连）                |
| **A** | Added to URT，已装进路由表                |
| **L** | **Advertised in LSPs，本机 LSP 里有这条** |
| **S** | IGP Shortcut 参与                    |
| **U** | Up/Down bit 置位（L2 泄漏到 L1）          |


**`L` 位是双稳态锁的物理证据：**

```
[R3] 5.5.5.5       Flags: A/-/-/-    学了但我不发  → 不可能是 IS-IS 的注入源
[R2] 10.0.34.0/24  Flags: D/-/L/-    直连，既入 RIB 又广告
```

R3 的 5.5.5.5 只有 A 没有 L，所以 R1 上 `Adv rtr 3.3.3.3` 那条 ASE，**是 R3 用 IS-IS→OSPF 反向灌回去的**，不是它从 IS-IS 引入的。

# 八、重分发为什么要查 RIB，而不是用 LSDB/缓存

R3 的 LSDB、OSPF 路由表里都有 5.5.5.5（缓了三份），但重分发不用。原因四条：

### ① 只有 RIB 做跨协议比较

OSPF 进程不知道 IS-IS 的存在，它算出的"最优"只在协议内成立。协议表里根本没有 preference 这张全局表。

### ② 导出必须等于转发现实

如果导出自己都不走的路，对端把流量送过来 → 你没有对应转发表项 → **黑洞**，或者你按另一条路送回去 → **环路**。

> **重分发的语义是"把我路由表里正在用的这条路翻译给你"，不是"把我听说过的所有路都告诉你"。**

### ③ 从 LSDB 导出必然成环且不收敛

```
R2 LSP 带 5.5.5.5 → R3 装进 LSDB → R3 导回 OSPF（因为 LSDB 里有）
→ R2 收到装进 LSDB → R2 导回 IS-IS → 无限循环
```

因为 **LSDB 没有"这条我已经发过了"的记忆**。RIB 方案至少提供了两个刹车：preference 压制 + 自产不回流。

### ④ RIB 还处理递归和下一跳可达性

下一跳是否可达、出接口是否 up、是否被更具体前缀覆盖、是否被 filter 挡住——全在 RIB 层判断。协议表里的条目可能下一跳已经不可达，导出去就是死路由。

## 这不是华为特例

| 厂商 | 命令 | 数据源 |
|---|---|---|
| Huawei VRP | `import-route ospf 1` | RIB |
| Cisco IOS | `redistribute ospf 1` | RIB |
| Juniper JunOS | `export policy` + `from protocol ospf` | RIB（`inet.0`） |
| FRR/Quagga | `redistribute ospf` | RIB（zebra） |
| BGP | `network x.x.x.x mask ...` | RIB（必须精确匹配且 Active） |

# 九、为什么 RIB 一变就驱动 IS-IS 重跑谓词

## 1. `import-route` 是长期订阅，不是一次性命令

```
RIB 每次变更
   → 主动向所有订阅者推送 delta（增量，不是全表）
        → 每条通知自带 "Proto + Process ID" 字段
             → IS-IS 用 import-route 规则做谓词过滤
                  → 命中的写进"重分发表"
```

你敲 `import-route ospf 1` 的那一刻，IS-IS 做的是：

1. 在 RIB 上**注册过滤器** `Proto==OSPF && ProcessID==1 && D位==1`
2. 立刻全表扫一次（这是"配置事件"触发）
3. 之后**长期监听**，每次相关变更就重跑谓词

## 2. RIB 推送的三种事件

| 事件 | 触发场景 | 动作 |
|---|---|---|
| **Add** | 新路由算出 / Inactive 变 Active | 命中则加入 |
| **Delete** | 路由彻底移除 | 移除 |
| **Modify** | 下一跳、cost、**preference、D 位**变了 | 重跑谓词，按新属性决定去留 |

**本实验走的是第三种 Modify**：

```
变更前：5.5.5.5 O_ASE  Pref 150  Flags D   ← 命中
变更后：5.5.5.5 O_ASE  Pref 150  Flags –   ← D 位被清除，不再命中
```

**这条路由既没增加也没删除，它一直在 RIB 里**，变的是状态位。**Modify 事件是让系统能自我纠正的关键**——如果只在 Add/Delete 时通知，本实验会卡死在错误状态：OSPF 条目还在但是 Inactive，IS-IS 却永远继续通告它。

## 3. 为什么不能等 900 秒刷新再算

那会形成最长 15 分钟的错误通告窗口：R3 持续告诉全网"5.5.5.5 从我这儿走，外部 cost 0"，但自己根本不这么转发。后果是次优路径或环路，双向场景下还会震荡放大。

**订阅保证快（毫秒级），节流保证不失控（50ms）。两个设计是配套的。**

## 4. 两个触发源别混

| 触发源 | 什么时候 | 干什么 |
|---|---|---|
| **配置事件** | 敲 `import-route` / `undo` / 改 route-policy | 全表重扫 + 重注册过滤器 |
| **RIB 变更事件** | 路由增/删/改（含 pref、D 位） | 只对变更项重跑谓词 |

**这就是"我配置都敲好了它却不干活"的原因**：配置事件只在敲下那一瞬间快照一次，后面全靠 RIB 事件驱动。而配置那一刻 R3 的 RIB 里 5.5.5.5 已经不 Active，所以那一刻就没抓到它。

恰恰 `0x80000006` 说明中间还翻转了几轮——说明配置的时候其实抓到了，后来又因为另一个方向注入了才撤回。

# 十、哪些命令订阅 RIB

## 真正订阅的（长期挂载的回调）

| 命令 | 视图 | 订阅什么 | 变更时做什么 |
|---|---|---|---|
| `import-route <proto> [pid]` | ospf/isis/rip/bgp | 该协议 **Active** 的路由 | 重算重分发表 → 重生 LSP/LSA |
| `default-route-advertise` | ospf | RIB 里 `0.0.0.0/0` 是否存在 | 决定是否生成默认 ASE |
| `default-route originate` | isis/rip | 同上 | 生成/撤销默认路由 |
| `network <prefix> [mask]` | bgp | RIB 中**精确匹配且 Active** | 加入 BGP 本地表并宣告 |
| `aggregate` | bgp | 明细路由是否存在 | 生成/撤销聚合路由 |
| `filter-policy export` | ospf/isis/rip | 重分发集合（二级过滤） | 过滤后重算发布集 |
| 下一跳递归（BGP） | bgp | 下一跳可达性 | 决定 BGP 路由是否有效 |
| `ip route-static ... track/bfd` | 系统 | 递归下一跳解析 | 安装/撤销静态路由 |

## 看着像订阅、其实不是

| 命令 | 为什么不是 |
|---|---|
| `display ip routing-table` | 一次性快照，执行完就结束 |
| PBR（`policy-based-route`） | 每报文查一次，不是订阅，路由变了它不知道 |
| `traffic-filter` / ACL | 作用在转发面 |
| `ospf enable` / `isis enable` | 从接口地址生成路由**推给** RIB，方向相反 |
| `route-policy` / `acl` / `ip ip-prefix` | 不订阅，但**被订阅者引用**；改了它引用者会重算 |

最后一条值得单独说：**route-policy 是间接触发器**。修改它本身不注册订阅，但所有引用它的 `import-route`、`filter-policy`、BGP peer policy 都会被重新评估。

## 一个反直觉点：订阅方向是从 RIB 向外的

RIB 不知道谁订阅了它，只在**自己的条目变化**时把 delta 推给所有回调。这意味着：

- 同一个前缀，如果 RIB 条目一条没变，所有订阅者都不会被调用——哪怕 IS-IS 的 LSP 已经变了十次
- 反过来，一个很小的 pref 变化（比如把 IS-IS preference 从 15 改成 20），会让**所有引用该前缀的订阅者同时重算**，可能引发全表范围的 LSP/LSA 重生

**这就是改 preference 危险的原因。**

## 顺带：为什么 R3 说"撤回"其实是"过滤掉"

RIB 里 OSPF 条目**仍然存在**（`O_ASE Pref 150 Inactive`），只是 D 位丢了。谓词不命中 → 不进重分发表 → LSP 重建时没有它。

准确说法是"**被过滤掉了**"，不是"消失了"。

# 十一、协议里有没有"来源"字段

**没有。** 这是这个环没法自动断的根本原因。

## IS-IS 侧能看到什么

| 能看到 | 出处 | 本实验实测 |
|---|---|---|
| 哪个 System ID 发的 | LSP 头 | R3 看到 `0000.0000.0002`（R2） |
| 是不是重分发进来的 | TLV 135 的 **X 位** | `Ext. Cost : 0`（直连的是 `NULL`） |
| 外部 cost | Ext.Cost | `0` |
| 管理 tag | TLV 135 sub-TLV | `Admin Tag : -`，**空的** |
| 到注入点的内部距离 | Int.Cost | `20` |

**X 位只表达"从 IS-IS 外部重分发进来的"，不表达"从哪个协议进来"。** `import-route ospf`、`import-route static`、`import-route direct` 进来后 X 位都是 1，长得一模一样。

## OSPF 侧也一样

Type-5 里有 Adv Router、Metric、E1/E2、Tag、Forwarding Address——同样**没有"源协议"字段**。Tag 是**唯一**能人工塞来源信息的槽位，而且是纯约定，协议不校验。

本实验 `Tag: 1` 是 `import-route direct` 默认打上的（华为默认 tag 1），不是标记 OSPF。

## 对比：有内建防环的机制

| 机制 | 防环手段 | 适用于 OSPF↔IS-IS？ |
|---|---|---|
| BGP | AS_PATH | ❌ 只有 BGP 认 |
| OSPF L1/L2 | LSA 的 **Down bit** | ❌ 只防 L1→L2→back |
| IS-IS L1/L2 | TLV 的 **Up/Down bit** | ❌ 只防域内泄漏 |
| MPLS VPN | RD/RT | ❌ |
| **OSPF↔IS-IS 重分发** | **无** | — |

**Tag 的作用，本质上是人工把"来源协议"这个缺失的字段补回去。协议没有，你自己写。**

## 重分发的本质

> **重分发是"无记忆的集合同步"，不是"逐条路由的账本"。**

R3 的注入循环：

```
RIB 变化 → 重分发表重算 → 取当前 RIB 中的 OSPF 路由集 → 与已发布集比对 → 有差异就重生 LSP
```

它比对的是**集合差**（现在是哪些），不是**变化原因**（为什么少了）。它不记得"这条来自 OSPF 所以我该删它"，只知道"上次有我这次没有，重发一版"。

# 十二、解决思路（本实验未实施）

## ① Tag 互斥（标准做法）

```
isis 1
 import-route ospf 1 tag 200
ospf 1
 import-route isis 1 tag 300 route-policy NO_BACK

route-policy NO_BACK deny node 10
 if-match tag 200
route-policy NO_BACK permit node 20
```

## ② 单点注入

只在一台 ASBR 上做双向，另一台只做单向或都不做。

## ③ `filter-policy import` 强制翻转角色

```
isis 1
 filter-policy 2000 import
acl 2000
 rule deny source 5.5.5.5 0
 rule permit
```

效果链：R3 的 IS-IS 路由表里 5.5.5.5 被过滤 → ISIS-L2 条目消失 → OSPF 版本重新变 Active 拿回 D 位 → RIB 推 Modify → IS-IS 重跑谓词命中 → LSP 重生 → **回灌者角色换边**。

注意：**只改了一处 filter-policy，`import-route ospf 1` 一个字没动**，它自己就开始工作——这是订阅机制的直接体现。

## ④ 改 preference（不推荐）

把 IS-IS preference 调到 200，OSPF 永远赢。但会让全网 IS-IS 域内路由都被 OSPF 压制，副作用很大，而且会触发大量订阅者同时重算。

## ⑤ 给引入加 cost（本实验遗漏的关键）

```
isis 1
 import-route ospf 1 cost 20
```

本实验 `Ext.Cost = 0`，意味着这条在 IS-IS 域内不比任何直连更贵，是环能轻易锁死的重要原因。

# 十三、排障命令清单

## 判断角色归属

```
[R2/R3] display isis route | include Redistribute -Context 0,20
[R2/R3] display ip routing-table 5.5.5.5 verbose
[R1]    display ospf lsdb ase 5.5.5.5
```

- 重分发表里有这条 → 这台在注入 IS-IS
- RIB 里哪个协议 Active → 决定这台能不能继续注入
- LSDB 里的 Adv rtr 有几个 → 有几个回灌者

## 判断 LSP 内容

```
display isis lsdb 0000.0000.0002.00-00 verbose
display isis lsdb local verbose
display isis route verbose          # 看 Int.Cost / Ext.Cost / Src Count / Flags
```

## 判断是否还在抖动

```
display ospf lsdb ase 5.5.5.5       # 记 seq，隔 2 秒再看
```

- seq 不动 → 已锁死
- seq 每 1~2 秒 +1 → 还在振荡带里，收敛态不可预测

## 恩威并施的错误示范

```
terminal monitor
terminal debugging
debugging ospf lsa
debugging isis lsp
debugging ip routing-table          # 看 RIB 推出去的变更事件
undo debugging all                  # 收工必关！
```

`debugging ip routing-table` 是验证"订阅是否被触发"最直接的证据。

# 十四、一句话总结

```
RIB 是裁判 → preference 是规则 → D 位是裁决结果
   → 订阅是通知机制 → 谓词是过滤器 → LSP 是快照
```

**你的 5.5.5.5 之所以"从 LSP 里消失"，不是因为老化、不是因为超时，而是裁判改了判，订阅者跟着更新了快照。**

双稳态锁能停下来，靠的就是这道闸门：**只有一边能通过 RIB 的 D 位检查。**

# 十五、这次会话的疑问与答案对照

| 疑问 | 答案 |
|---|---|
| 引入 IS-IS 是引入路由表里的 OSPF 路由吗 | 是，但只取 RIB 中 **Active** 的那部分 |
| 为什么 R1 上两条等价路由，一条下一跳是 R3 不是 R2 | 两条都在表里（ECMP），R2 的角色是 OSPF→IS-IS，不负责回灌 |
| R3 也配了引入，为什么不是 R3 注入 IS-IS | R3 的 OSPF 版本是 Inactive，`import-route ospf` 抓不到 |
| 是先配置顺序导致的吗 | 不是时序的一次性结果，是 preference 决定的稳定结构 |
| 新加一条外部路由会被谁回灌 | 首发时两台都注入；回灌时默认两台都回灌（3 条）；抖动后可能只剩一台，不可预测 |
| 为什么反复撤销 | 存在正反馈环，T3 两台同时撤回、T4 同时恢复 |
| LSP-Throttle 是什么 | 同一条 LSP 两次生成的最小间隔，默认 50ms，合并而非丢弃 |
| 5.5.5.5 消失是老化吗 | 不是。老化粒度是整条 LSP；这里是内容变更重生，序列号 +1 |
| 为什么去 RIB 查而不是用缓存 | 只有 RIB 做跨协议比较；导出必须等于转发现实；从 LSDB 导出必然成环 |
| 为什么 RIB 一变就重跑谓词 | `import-route` 是长期订阅，RIB 推 delta（含 Modify 事件） |
| 哪些命令订阅 RIB | 重分发族、默认路由生成族、BGP network/aggregate、静态路由递归 |
| IS-IS 知道这条来自 OSPF 吗 | 不知道。协议没有来源字段，只有 X 位表示"来自外部"，Tag 要人工打 |
